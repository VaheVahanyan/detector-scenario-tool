# detector-scenario-tool

Локальное desktop-приложение на PySide6 для редактирования циклограмм работы детектора NATALIA
(гамма-спектрометр, плата управления на STM32L496ZG).

Текущая версия протокола — **`Протокол_CAN_ГС_v2_1_Спутникс`**: 17 команд управления (КУ),
3 команды телеметрии (КТ), 5 телеметрических сообщений (ТС).

## Установка

Системный Python помечен как externally-managed (PEP 668), поэтому работаем в venv:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e ".[dev,serial]"
```

Дополнительные группы зависимостей:

| Группа | Назначение |
|---|---|
| `serial` | live-захват отладочных логов детектора через последовательный порт |
| `can` | live-обмен по CAN через переходник CANable |
| `dev` | pytest + pytest-qt |

## Запуск

```bash
.venv/bin/detector-scenario-tool
# или
.venv/bin/python -m detector_scenario_tool.app.main
```

## Тесты

```bash
.venv/bin/python -m pytest              # весь набор
.venv/bin/python -m pytest tests/protocol -q
.venv/bin/python -m pytest -k golden_vectors
```

Тесты выполняются headless — `tests/conftest.py` выставляет `QT_QPA_PLATFORM=offscreen` до импорта
PySide6. Тестам, создающим виджеты, нужна фикстура `qapp` или `qtbot`.

Если сборка тестов падает с `libQt6DBus.so.6: undefined symbol`, системный Qt6 перекрывает тот,
что поставляется с PySide6. Само приложение при этом работает; лечится так:

```bash
export LD_LIBRARY_PATH=$(.venv/bin/python -c \
  "import PySide6, os; print(os.path.join(os.path.dirname(PySide6.__file__), 'Qt', 'lib'))")
```

## Подключение к железу

Приложение работает и без переходника: бэкенд по умолчанию — **симуляция детектора**, она отвечает
по тем же правилам протокола (квитанции, коды ошибок, допустимость команд по режимам), поэтому
сценарий можно прогнать целиком до подключения к стенду.

Для реального обмена нужен `pip install -e ".[can]"` и CANable. Прошивка бывает двух видов, и
настраиваются они по-разному:

| Прошивка | Как выглядит | Кто задаёт скорость |
|---|---|---|
| candleLight / gs_usb | интерфейс SocketCAN, например `can0` | ядро — нужен `ip link` |
| slcan | последовательный порт, например `/dev/ttyACM0` | само приложение, по шине |

Для **SocketCAN** в панели подключения есть кнопка «Настроить интерфейс»: она показывает, какая
именно команда будет выполнена, затем система запрашивает пароль администратора своим штатным
окном (PolicyKit). Приложение пароль не видит и не сохраняет, и больше ничего с правами
администратора не выполняет — сам обмен идёт от обычного пользователя. То же самое вручную:

```bash
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 1000000
sudo ip link set can0 up
```

Для **slcan** ничего настраивать не нужно: выберите бэкенд, укажите `/dev/ttyACM0` и скорость.

Шина CAN1 работает на скорости 1 Мбит/с (CAN 2.0B). Адреса по умолчанию: БВС КА `05h`, НА `1Eh`.

Перед первой реальной передачей приложение спрашивает подтверждение, а пока подключение активно
показывает красную полосу **LIVE**.

**Шина читается всё время, пока открыто подключение** — не только во время прогона сценария. Всё,
что появляется на шине до, между и после прогонов, попадает в лог: и телеметрия, и отладочный вывод
платы, и поздний ответ, пришедший уже после того, как шаг перестал его ждать. Читает всегда кто-то
один: пока есть прогон — он, в остальное время — монитор шины.

Кто есть кто на шине: адреса лежат внутри CAN-идентификатора, и участников двое — компьютер (БВС,
по умолчанию `05h`) и НА (`1Eh`). Переходник CANable адреса не имеет вообще и сам ничего не
отвечает: он прозрачный. При 11-битных идентификаторах и адресах по умолчанию наши кадры уходят с
`0x0BE`, а ответы НА приходят с `0x3C5`.

Оба адреса задаются в панели подключения полями **БВС** и **НА** (в шестнадцатеричном виде, слева
направо — отправитель и получатель наших команд). В протоколе адрес НА помечен как предварительный,
и на стенде плате мог быть выдан другой, поэтому это настройка подключения, а не константа. Диапазон
следует ширине идентификатора: 5 бит (`00…1F`) для 11-битных кадров и 14 бит (`0000…3FFF`) для
29-битных. Значения запоминаются между запусками, а команды «Задание адреса получателя» и «Задание
адреса устройства» по-прежнему могут сдвинуть адреса уже по ходу прогона — в полях задаётся то, с
чего прогон начинается.

## Если на стенде прошивка версии v2

Приложение работает только по v2.1. Если МК ещё отвечает по старой нумерации, его сообщения видно в
логе с пометкой вида «Нумерация протокола v2: сейчас это ТС 0x0D01 Квитанция» — то есть связь есть,
но версии протокола разные. Шаг ожидания таким сообщением **не закрывается**: это диагностика, а не
поддержка старой версии.

Первое, что стоит проверить, если ответов не видно вообще:

| Что | Как проверить |
|---|---|
| ширина идентификаторов | галка «29-битные идентификаторы» в панели подключения должна совпадать с прошивкой |
| скорость | 1 Мбит/с с обеих сторон; для SocketCAN её задаёт ядро, а не приложение |
| адреса | поля «БВС» и «НА» в панели подключения должны совпадать с тем, что прошито на плате |
| шина | без второго узла и терминаторов 120 Ом кадр не получает подтверждения и уходит в bus-off |

## Отладочный вывод платы в шине CAN

В некоторых конфигурациях МК печатает собственные отладочные сообщения в ту же шину CAN. Это **не
UniCAN**: прошивка (`BSP/UART/src/log_backend_can.c`) шлёт их на одном постоянном идентификаторе
`7DBh`, а в кадре лежит чистый текст — ни адресов, ни MSG_ID. Приложение узнаёт такие кадры по
идентификатору и разбирает их отдельно, **до** сборки длинных сообщений.

Это не косметика. Если прочитать `7DBh` по правилам UniCAN, получается «кадр данных длинной
передачи от адреса `1Eh`» — а `1Eh` это адрес самой НА. То есть до этой правки байты лога
дописывались внутрь идущей телеметрии и разрушали её, а сами оказывались в логе битым кадром.

Что это значит на практике:

- строка показывается **текстом**, а не байтами (кириллица тоже; если содержимое на текст не
  похоже, приложение так и говорит и оставляет hex в своём столбце);
- кадры **собираются обратно в строки** по переводу строки: прошивка ставит `\r\n` в конце каждой,
  а границы кадров к границам строк отношения не имеют (строка режется сначала по 32 байта, потом
  по 8). В столбце «кадров» видно, из скольких кадров собралась строка. Строка без перевода строки
  (так печатаются отдельные числа) выводится, когда плата замолкает на четверть секунды;
- она **не закрывает шаг ожидания** и не может выдать себя за квитанцию;
- она **не участвует в сопоставлении** сценария с логом — не считается лишним логом, не становится
  «первым расхождением» и не блокирует выполнение;
- в фильтре по категориям у неё своя строка «Лог», так что вывод платы можно и посмотреть
  отдельно, и убрать с глаз, выбрав любую другую категорию;
- она видна и вне прогона — достаточно быть подключённым.

Идентификатор задаётся полем **«Лог платы»** в панели подключения (по умолчанию `0x7DB`): это
константа прошивки, а не протокола, и в другой сборке она может быть другой.

Отдельно от этого остаётся правило для сообщений, которые **пришли по UniCAN правильно**, но
которых нет в каталоге как ТС: команда управления, вернувшаяся по шине, или ответ по старой
нумерации v2 — тоже лог, а не ответ НА.

В сохранённом логе такие строки помечены `cat=LOG` — это единственная категория, которую нельзя
восстановить по каталогу задним числом, поэтому она пишется в файл.

## Научные данные (режим вывода)

Поток НИ идёт **не по CAN, а по USB** — через микросхему FTDI на плате управления (её сигналы
`PU_FTDI_PS`, `PU_FTDI_PSON`, `PU_FTDI_RES` видны в слове «Статус НА»). На Linux ядерный драйвер
`ftdi_sio` показывает её как `/dev/ttyUSB0` — это значение по умолчанию во вкладке «Пакеты».
Отдельных драйверов ставить не нужно, достаточно доступа к порту:

```bash
sudo usermod -aG dialout $USER      # нужен перезаход в систему
```

Если поток идёт рывками, уменьшите задержку FTDI (по умолчанию 16 мс):

```bash
echo 1 | sudo tee /sys/bus/usb-serial/devices/ttyUSB0/latency_timer
```

Проприетарный драйвер **D2XX** сейчас не поддерживается и в общем случае не нужен: он даёт больший
поток, но **конфликтует с `ftdi_sio`** — чтобы его задействовать, ядерный модуль пришлось бы
выгрузить и заблокировать, после чего `/dev/ttyUSB0` исчезнет и работать придётся по серийному
номеру устройства. Имеет смысл возвращаться к этому, только если упрётесь в скорость на стенде.

## Каталог команд

Меню «Правка → Каталог команд» показывает единым списком все сообщения: описанные в протоколе и
добавленные сценарием. В столбце «Источник» видно, что есть что — *из протокола*, *изменена*,
*своя*, *скрыта*. Оттуда же они добавляются, правятся, удаляются и восстанавливаются.

Встроенные описания живут в коде (`protocol/definitions/`) и никогда не перезаписываются: сценарий
хранит только свои правки поверх них. Поэтому «Восстановить» всегда возвращает команду к виду из
протокола, а «Восстановить все встроенные» откатывает разом всё, не трогая собственные команды
сценария.

Изменение встроенной команды необратимо теряет часть описания — типы полей, перечисления и проверки
содержимого из спецификации заменяются байтами с именами. Приложение предупреждает об этом до, а не
после.

## Старые файлы сценариев

Сценарий, сохранённый до перехода на v2.1, открывается как есть: идентификаторы перенумеровываются
автоматически (КУ 1–13 сдвинулись на `+0F00h`, КТ «Мак-Илвайн» `0100h` → `0E00h`, ТС `0200h…0203h`
→ `0D00h…0D03h`), содержимое команд при этом не менялось. Что было изменено, перечислено в панели
предупреждений.

Два случая требуют внимания, и о каждом приложение говорит отдельно:

- **Начальное приборное время RTC** в «Задании настроек» разделилось на миллисекунды и секунды.
  Прежнее значение переносится в секунды, миллисекунды выставляются в 0.
- **Своя команда может столкнуться с встроенной**: `0F01h`, например, был свободен, а теперь это
  «Запрос статуса». Смените идентификатор или отметьте команду как замену встроенной.

Файлы ещё более ранней версии (до v2) переносятся иначе: их команды телеметрии **отключаются** с
сохранением исходного JSON, потому что там один и тот же `0100h` означал другое сообщение другой
длины. Такой шаг нужно создать заново вручную.
